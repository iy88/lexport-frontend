# LexPort Frontend MVP Production Fix Plan

## 1. Purpose and delivery boundary

This document is the self-contained implementation specification for adapting the React frontend to the backend MVP production fixes. The implementation agent must not rely on prior conversations.

The frontend remains a React/Vite application using Redux authentication, Axios, and Bearer JWTs stored in `localStorage`. Do not move tokens to cookies and do not add CSRF handling.

This work intentionally excludes:

- frontend automated tests;
- lint-pipeline repair;
- installing or configuring ast-grep;
- modifying `.rules/*.sh`;
- fixing the `/workspace/.dist` path in the unused generated build script;
- deployment/hosting configuration.

The implementation agent should ensure the normal production build compiles. The user will perform the manual frontend acceptance defined in this document.

## 2. Current frontend defects

1. `/admin` uses only authentication protection. A normal user can navigate directly to admin routes even when the sidebar hides their links.
2. News and Agency pages infer pending review solely from `status==='draft'`, which cannot represent a published live version with pending changes.
3. Batch approval also selects only main-table drafts and misses published items with a Draft row.
4. News/Agency admin pages lack a discard-pending-draft action.
5. Registration labels email as optional even though verified email will be required for reports.
6. There is no account UI for binding/replacing email or resending verification.
7. The report client does not send an Idempotency-Key, so response loss and retry can create duplicate paid tasks.
8. Report status types do not include `submitting`.

## 3. Backend contract consumed by the frontend

The frontend implementation must use the following fixed backend behavior.

### 3.1 Roles

- `user`: public pages, account pages, own reports; no `/admin/*` access.
- `editor`: content management and reference-data read/create/update; no approval, suspension, draft discard, reference delete, user management, or all-report management.
- `admin`: all routes and actions.
- Editors share content drafts; the UI must not present draft ownership or locking concepts.

### 3.2 Review fields

News and Agency admin list/detail items include:

```ts
type ReviewStatus = 'pending' | 'none';

interface ReviewableItem {
    status: 'draft' | 'published';
    has_draft: boolean;
    review_status: ReviewStatus;
}
```

- `published + has_draft + pending` means the old published version is live and the backend detail response contains a merged preview of pending changes.
- `draft + !has_draft + pending` means a never-published main-table draft.
- `published + !has_draft + none` means no pending work.

Admin list APIs accept `review_status=pending|none`.

Draft discard endpoints are:

```http
DELETE /api/admin/news/{id}/draft
DELETE /api/admin/agencies/{id}/draft
```

They are admin-only and apply only to a separate Draft on a published item.

### 3.3 Registration and email APIs

Registration request requires email:

```json
{
  "username": "example_user",
  "password": "example123",
  "email": "user@example.com"
}
```

Registration success data adds:

```ts
interface RegisterResult {
    user: User;
    access_token: string;
    verification_email_sent: boolean;
}
```

Registration returns 201 even when email delivery fails; in that case the account/token remain valid and `verification_email_sent=false`.

Email change:

```http
PUT /api/user/email
Authorization: Bearer <token>
Content-Type: application/json

{"email":"new@example.com","password":"current-password"}
```

Response data:

```ts
interface UpdateEmailResult {
    user: User;
    verification_email_sent: boolean;
}
```

Resend:

```http
POST /api/user/email/resend-verification
Authorization: Bearer <token>
```

The combined email change/resend limit is five per hour per user. A breach is 429 `RATE_LIMITED`.

Email verification remains:

```http
POST /api/auth/verify-email
{"token":"..."}
```

Unverified report creation fails with 403:

```json
{
  "success": false,
  "error": {
    "code": "EMAIL_VERIFICATION_REQUIRED",
    "message": "请先验证邮箱后再创建合规报告"
  }
}
```

### 3.4 Report idempotency API

Every new report request requires:

```http
Idempotency-Key: <UUID generated by crypto.randomUUID()>
```

Backend semantics:

- same user/key/payload returns the existing report and never repeats OSS/Bailian work;
- same user/key with changed payload returns 409 `IDEMPOTENCY_CONFLICT`;
- a failed report remains bound to that key;
- intentional new generation requires a new key;
- submitting/queued/in_progress responses use 202;
- completed/failed/cancelled idempotent replays use 200.

Report status types add:

```ts
type ReportStatus =
    | 'submitting'
    | 'queued'
    | 'in_progress'
    | 'completed'
    | 'failed'
    | 'cancelled';
```

`submitting` must be displayed as `正在提交`.

## 4. Role-based routing and navigation

### 4.1 RequireRole behavior

Add a reusable route guard that accepts an allowed-role array.

- While authentication initialization is incomplete, render the same loading behavior as the existing auth guard.
- If no current user exists, redirect to login with the existing redirect query behavior.
- If authenticated but role is disallowed, show a “权限不足” toast once and replace-navigate to `/user`.
- Do not render the protected page before redirect.

### 4.2 Route mapping

| Route | Roles |
|---|---|
| `/admin/laws` | admin, editor |
| `/admin/news` | admin, editor |
| `/admin/agencies` | admin, editor |
| `/admin/reference/*` | admin, editor |
| `/admin/users` | admin |
| `/admin/reports` | admin |
| `/admin/reports/:id` | admin |

Keep backend authorization as the security boundary; the frontend guard is navigation and UX enforcement.

### 4.3 Sidebar

- user sees dashboard and own reports only.
- editor sees dashboard, own reports, content management, and every current reference-data page.
- admin additionally sees user management, all-report management, and admin-only operations.
- Existing localStorage token and Axios Authorization interceptor remain unchanged.

## 5. Registration and account email UI

### 5.1 Registration form

- Change email label and validation from optional to required.
- Prevent submission when email is empty or invalid.
- Continue storing the returned access token and User through the current Redux flow.
- Extend the register thunk/result type with `verification_email_sent`.
- When true, show `注册成功，请查收验证邮件`.
- When false, registration is still successful: navigate to `/user` and show `账号已创建，但验证邮件发送失败，请在账户页重试`.

Do not turn a 201 response with `verification_email_sent=false` into a rejected Redux action.

### 5.2 UserDashboard email section

Replace the read-only email-status card with an account email section containing:

- current email or `未绑定`;
- verified/unverified badge;
- `重新发送验证邮件` button when email exists but is unverified;
- `绑定邮箱` or `更换邮箱` action;
- a dialog/form with new email and current password;
- submitting/disabled states to prevent duplicate clicks.

After email change:

- update Redux User from the response immediately;
- display success if mail was sent;
- display a warning and keep the unverified new email if `verification_email_sent=false`;
- clear the password field in all outcomes.

Resend handling:

- 200: show success;
- 409 already verified: refresh profile and show the backend message;
- 429: show a specific “操作过于频繁” message;
- 502: show that email delivery is temporarily unavailable and preserve the retry control.

### 5.3 Verification page

- Keep POSTing the route token to `/auth/verify-email`.
- On success, if the user is currently logged in, dispatch `fetchProfile()` so `email_verified` updates without another login.
- Logged-in success action returns to `/user`; logged-out success action returns to `/login`.
- Preserve safe backend error messages for expired/invalid tokens.

### 5.4 Report-page verification gate

- Read the current User from Redux before submission.
- If `email_verified` is false, do not build FormData or call the API; show an explanation and an action/link to `/user`.
- Still handle backend 403 `EMAIL_VERIFICATION_REQUIRED`, because the database state may change in another session.
- For that 403, show the same guidance and navigate/link to the account page rather than a generic error.

## 6. Report idempotency implementation

### 6.1 API helper

Change the report creation helper signature to:

```ts
createComplianceReport(
    formData: FormData,
    idempotencyKey: string,
): Promise<CreateReportResponse>
```

Send it as `Idempotency-Key`; do not put it inside FormData or persist it globally.

### 6.2 Form submission identity

The diagnosis page keeps a ref/state containing:

```ts
interface SubmissionIdentity {
    signature: string;
    key: string;
}
```

Build a deterministic client signature from:

- trimmed form text values in a fixed order;
- attachment descriptors in displayed/submitted order: filename, size, MIME type, and `lastModified`.

The client signature is only used to decide whether a click is a retry. The backend content fingerprint remains authoritative.

Rules:

1. If no identity exists, generate `crypto.randomUUID()` and store it with the signature.
2. If the current signature matches the stored signature after an error, reuse the key.
3. If any field or attachment changes, replace the identity with a new key on the next valid submit.
4. On success, clear the identity before navigation.
5. Loading `/diagnosis?regenerate={id}` starts with no identity, so submitting the prefilled form creates a new report.
6. Keep the identity after network/5xx/unknown-result errors so a retry is safe.

### 6.3 Responses and errors

- A successful replay may return an existing report. Always navigate using the returned `result.id`; do not assume it is newly created.
- On 409 `IDEMPOTENCY_CONFLICT`, clear the stored identity, show `提交内容已变化，请重新提交`, and do not automatically retry.
- On 429 `RATE_LIMITED`, preserve the identity and show `提交过于频繁，请稍后重试`.
- On other errors, preserve the identity unless the user changes input.
- Extend all status-label/type maps for `submitting`.

## 7. News and Agency review UI

### 7.1 Status presentation

Stop treating `item.status === 'draft'` as the sole pending test. Use:

```ts
const isPending = item.review_status === 'pending';
const isUnpublishedDraft = item.status === 'draft';
const isPublishedWithDraft = item.status === 'published' && item.has_draft;
```

Display:

- unpublished draft: `待首次审核`;
- published with Draft: both `已发布` and `有待审修改`;
- published without Draft: `已发布`.

### 7.2 Filters and batch actions

- Add/use `review_status` filtering where the backend provides it.
- Admin batch selection includes every `review_status='pending'` item.
- After approve/discard/suspend, clear selected IDs that are no longer pending and refresh the list.
- Editor never sees checkboxes or approval actions.

### 7.3 Editing previews

- News edit must fetch detail and populate the form from the backend merged Draft preview, including draft `content` and draft tags.
- Agency edit must fetch detail rather than relying only on list data, ensuring pending preview fields are used consistently.
- Shared editor behavior requires no ownership display or lock warning.

### 7.4 Admin actions

For a pending item:

- admin sees approve;
- admin sees discard only when `has_draft=true` on a published item;
- admin sees suspend according to backend eligibility;
- editor sees edit only.

Discard must use a confirmation dialog explaining that the current published version remains live. Use the News or Agency discard endpoint according to resource. Surface 400/404/409 backend messages without pretending the action succeeded.

## 8. Manual acceptance checklist

The user will perform frontend acceptance. The implementation agent should provide a concise handoff listing the build result and any behavior that requires a running backend.

### 8.1 Roles

- user cannot render any `/admin/*` page by entering the URL directly;
- editor can open content/reference pages but not users/all-reports;
- admin can open all admin pages;
- sidebar and route guards agree for every role;
- editor has no approve/suspend/discard/reference-delete controls.

### 8.2 Email

- registration blocks empty/invalid email;
- successful registration shows verification guidance;
- SMTP-failed registration remains logged in and offers resend;
- binding/replacing email requires current password;
- resend success, rate-limit, and delivery-failure messages are distinct;
- successful verification refreshes the logged-in User;
- unverified users cannot submit a report and are guided to `/user`.

### 8.3 Idempotency

- a simulated response/network failure followed by unchanged retry reuses the same key and opens the same report;
- changing any form field or attachment after failure creates a new key;
- regenerate always creates a new key;
- conflict and rate-limit errors show the specified messages;
- submitting status renders without falling into an unknown-state UI.

### 8.4 Review workflow

- editor modification of published News/Agency displays a pending marker while the public page retains old content;
- a second editor can open and continue editing the shared preview;
- News preview includes pending正文 and tags;
- admin batch approval selects published-with-Draft items;
- admin approval exposes the new version publicly;
- admin discard removes the pending marker and preserves old public content.

## 9. Completion criteria

The frontend implementation is complete when:

- the normal production build succeeds;
- role guards and sidebar mappings implement the exact matrix above;
- registration/account/report flows implement the email-verification contract;
- every report POST carries the correct retry-stable Idempotency-Key;
- News/Agency pages use review fields rather than status alone;
- the user completes the manual checklist;
- no changes are made to token storage, lint scripts, ast-grep configuration, `/workspace/.dist`, hosting configuration, or frontend test infrastructure.
